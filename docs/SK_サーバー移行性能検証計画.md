# SK（債権管理課）サーバー移行 性能検証計画

**作成日**: 2026-08-04

## 背景・目的

- SK では、データ用 Access（バックエンド）をネットワークフォルダーに置き、各 PC の UI 用 Access（フロントエンド）からリンクテーブルで参照する分割構成で運用している。
- 今回、バックエンドを置くサーバーがリモートネットワーク上の新サーバーに変わるため、**移行後も業務に耐える性能が出るか**を事前に検証する。

## 検証の考え方（重要）

リンクテーブル運用の Access は、**帯域（MB/秒）よりもネットワーク遅延（RTT）に極端に敏感**。
Access はバックエンド mdb に対して SMB 経由で細かい読み書き（ページ単位のロック・読み取り）を大量に往復させるため、

- ファイルコピーの速度（帯域）が十分でも、
- RTT が LAN の 1ms 未満 → リモートの 数ms〜数十ms に増えると、

検索・入力などの**1操作あたりの応答が数倍〜数十倍に劣化**しうる。
したがって「大容量コピーが速いか」ではなく、**「1操作あたり何 ms か」を新旧サーバーで比較**するのが本検証の中心。

## 検証ツール

| ファイル | 役割 | 実行環境 |
|---|---|---|
| `src/SK/modBenchmark.bas` | Access 実操作のベンチマーク。検証専用バックエンド（bench_backend.mdb）を対象フォルダに自動生成して測定。**本番データには触らない** | SK の実運用 PC の Access（VBA） |
| `src/SK/network_baseline.ps1` | ネットワーク素の性能（RTT・帯域・小ファイル多数操作）を測定。Access の結果が悪い場合の原因切り分け用 | 同 PC の PowerShell |

## 測定項目と見るポイント

| # | テスト項目 | 何に相当するか | 敏感な要素 |
|---|---|---|---|
| 1 | DB接続（共有オープン） | 起動時・朝一の接続、ldb ロック作成 | 遅延 |
| 2 | 一括INSERT（トランザクション） | 夜間バッチ的な一括処理 | 帯域寄り |
| 3 | 逐次INSERT（1件ずつ） | 画面からの入力・保存操作 | **遅延（最重要）** |
| 4 | 全件集計（COUNT/SUM） | 集計・帳票 | 帯域＋遅延 |
| 5 | 全件読み取り | 一覧表示・エクスポート | 帯域 |
| 6 | インデックス検索（1件ずつ×100回） | 画面での検索・参照操作 | **遅延（最重要）** |
| 7 | 一括UPDATE | 一括更新処理 | 帯域＋遅延 |
| 8 | リンクテーブル経由の検索 | 本番と同じ参照形態での体感 | 遅延 |

## 実施手順

1. 新旧両サーバーの共有上に、本番フォルダとは別の**検証専用サブフォルダ**を用意する。
2. SK の**実際に業務で使う PC** で実施する（検証者の高性能 PC ではなく）。
3. `network_baseline.ps1` を旧・新それぞれに対して実行。
4. 新規の空 Access ファイルを作り、`modBenchmark.bas` を貼り付けて、イミディエイトウィンドウで:
   ```
   BenchRun "旧サーバー", "<<旧サーバーの検証用フォルダUNCパス>>"
   BenchRun "新サーバー", "<<新サーバーの検証用フォルダUNCパス>>"
   ```
   （各3回の反復は自動。時間帯の影響を見るため、**業務時間帯とアイドル帯の2回**実施が望ましい）
5. 結果 CSV（`bench_results.csv` / `network_baseline_results.csv`）を回収し、新旧比較表を作成。
6. 終了後 `BenchCleanup "<<検証用フォルダUNCパス>>"` と検証フォルダ削除で後片付け。

## 判定の目安

| 指標 | 目安 |
|---|---|
| ping RTT | 新サーバーで **5ms 以下**なら概ね安心。10ms 超は体感劣化の可能性大、20ms 超は対策必須級 |
| 逐次INSERT・検索の ms/件 | 新旧比 **1.5倍以内**なら許容圏。2倍超なら利用者が「遅くなった」と感じるレベル |
| 大容量コピー | 劣化していても、上2つが良好なら業務影響は限定的 |

## 性能が出なかった場合の対策候補（先出し）

| 案 | 内容 | 備考 |
|---|---|---|
| A | フロントエンド側で「常時接続保持」（起動時にバックエンドへのダミー接続を開きっぱなしにする） | ldb 開閉のオーバーヘッド削減。定番・低コスト |
| B | リモートデスクトップ / RemoteApp 化（Access をサーバー側で動かし画面だけ飛ばす） | 遅延問題を根本解消。環境構築が必要 |
| C | バックエンドを SQL Server（Express 可）等へ移行 | 抜本対策だが工数大。別見積案件 |
| D | サーバー側の SMB 設定・ウイルス対策スキャン除外の調整 | 情報システム部門との調整事項 |

## 注意事項

- 検証ツールは本番 mdb・本番フォルダに一切書き込まない設計だが、念のため検証フォルダは本番と分けること。
- VPN・拠点間回線を経由する場合は、実際の業務経路と同じ経路で測ること。
- ウイルス対策ソフトのリアルタイムスキャンが mdb/ldb に効いていると大きく劣化する。新旧で設定差がないか確認。
- 実測結果の CSV（個社のサーバー名等を含む）はこのリポジトリにコミットしない。

## 論点

- 新サーバーの「リモートネットワーク」が拠点間 WAN・VPN・クラウド（Azure Files 等）のいずれなのかで、想定 RTT と対策の打ち手が変わる
- 検証は旧サーバーが生きているうちに実施する必要がある（A/B 比較のため）
- 判定の目安（1.5倍・5ms 等）は一般論ベースの仮置き。実測後、業務の操作頻度（1日の入力件数・検索回数）と掛け合わせて許容可否を判断するのがよい
