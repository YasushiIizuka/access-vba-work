# WORCS 開発の注意点（再発防止メモ）

## 「登録日」等の同名フィールドは必ずテーブル名で修飾する

**T_WORCS と T_WORCS_Check には同名のフィールドがある**（少なくとも
登録日・更新日・受注番号・商品コード・No）。
このため、両者を結合したクエリ（Q_特定5講座 など）を相手にするときは、
**SQL・Filter・RowSource・抽出条件のどこであっても、フィールド名を
テーブル名で修飾する**こと。

- NG: `[登録日] = #2026/07/31#`
- OK: `[T_WORCS].[登録日] = #2026/07/31#`

修飾しないと **エラー3079「指定されたフィールドが SQL ステートメントの
FROM 句にある複数のテーブルを参照しました」** になる。

### 発生履歴（2回）
1. **2026-07-17**: cbo対象日 の RowSource を結合クエリから作ろうとして発生
   → テーブル（T_WORCS）直指定で回避
2. **2026-07-31**: 対象日の絞り込みをコードの Filter に移した際、
   `[登録日] = #…#` と書いて発生 → `[T_WORCS].[登録日]` に修飾して解消

### 修飾時の注意
- クエリ内で T_WORCS が**別名（エイリアス）**になっている場合は、
  デザイングリッドの「テーブル」行に表示されている名前で修飾する

## Forms! の絶対参照はナビゲーションフォームで壊れる（2026-07-31）

クエリの抽出条件に `[Forms]![フォーム名]![コントロール名]` と書く方式は、
そのフォームを**ナビゲーションフォームに埋め込むと参照が解決できず
「パラメーターの入力」ダイアログが出る**（埋め込まれたフォームは
Forms コレクションに単独では存在しないため）。

- 対策: 絞り込みはクエリの抽出条件ではなく、**コードで Filter を組み立てて
  適用**する（F_特定5講座 は 2026-07-31 にこの方式へ移行済み）
- フォーム内の参照は `Parent!` などの**相対参照**であれば埋め込みの影響を受けない

## テーブル名を変更したら、参照の総点検をセットで行う（2026-07-31）

テーブル名を変更すると、旧名で参照している場所が芋づる式に壊れる。
しかもエラーメッセージが分かりにくい:

- クエリの参照先テーブルが無い状態でフォームを開くと、
  **「レコードソース ○○（クエリ名）は存在しません」**と出る
  （クエリはあるのに、と混乱する。実際はクエリの中身の参照切れ）

「名前の自動修正」はクエリ等をある程度追従するが、
**VBA コード内の SQL 文字列・DCount/DLookup の引数は対象外**。

### 変更時のチェックリスト
1. そのテーブルを使うクエリを開いて確認（対になるクエリも忘れずに。
   例: Q_再注レター印刷 と Q_代引きレター印刷）
2. VBE で Ctrl+F → 検索対象「カレント プロジェクト」で旧テーブル名を検索
3. フォーム・レポートのレコードソース／コンボの値集合ソース

### 発生履歴
- 2026-07-31: テーブル名を T_WORCS_Check に変更した影響で
  Q_再注レター印刷 が参照切れ → F_再注レター印刷 が開けなくなった

## フォームモジュールの全文差し替えは、現行コードを受領してから

貼り付け先モジュールに既存コードがあるかを確認せずに「全文差し替え」を
指示すると、既存機能のコードが消える（2026-07-24 に選択チェックの
色つけ・並べ替えコードが消失し、作り直しになった）。
差し替え指示の前に、**inbox 経由で現行モジュールを受領して差分を確認**する。
